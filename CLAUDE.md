# Avenas

iOS-first React Native + Expo (SDK 57, RN 0.86, New Architecture), TypeScript strict. Expo Router + NativeTabs. Shipped to App Store.

## Non-obvious rules

- **StyleSheet only** — no Tailwind, no styled-components.
- **Packages: `npx expo install`**, never `npm install`. This tree resolves with `--legacy-peer-deps` (an optional `react-native-windows` peer on `@react-native-community/datetimepicker` otherwise fails resolution), so pass `-- --legacy-peer-deps`.
- **Never import `@react-navigation/*`** — expo-router dropped react-navigation in SDK 56 and importing it fails the bundle. `useFocusEffect` and friends come from `expo-router`.
- **`StyleSheet.absoluteFill`**, not `absoluteFillObject` — the latter was removed in RN 0.86.
- **Lists:** `FlashList`. **Images:** `expo-image`. **Secrets/tokens:** `expo-secure-store` (not AsyncStorage).
- **Colors:** `constants/theme.ts` (`ACCT`, `APP_LIGHT`, `APP_DARK`, `NEU_BG`) — no hex literals in screens. **Lines use `t.div` in both themes** (dividers, hairlines, borders, chart `rulesColor`/`xAxisColor`, quiet fills): dark's is a translucent white, so it lifts off cards and the page alike. It was a solid navy identical to the card colour, which made every dark-mode line invisible and bred ~32 `isDark ? "rgba(255,255,255,0.1)" : t.div` workarounds; don't reintroduce that idiom.
- **Safe areas:** `useSafeAreaInsets()` — never hardcode inset values.

## Components to reuse

- **Cards:** `NeuCard`. **Buttons:** `BounceButton` (primary = `ACCT` bg + `ACCT` shadow glow).
- **A program, read-only:** `components/ProgramSnapshotView.tsx` — the cycle strip plus one card per day with its exercises, sets, rest and notes, weights expressed in the viewer's unit. Used by `app/program-view.tsx` (a program someone sent) and `app/trainer/review/[id].tsx` (a program someone asked you to review). They are the same program seen from the two ends of one flow, so they must read identically; the review screen used to list bare exercise names, leaving a trainer to judge programming they couldn't see. Both open with `components/ProgramHeaderCard.tsx` (name, weeks, training days, cycle length) under an uppercase screen title — the viewer used to show the name as its title and the rest as bare grey text on the page, so every "View" button on the trainer and group pages opened to something plainer than the review screen. Both screens also carry `components/ProgramActionFabs.tsx` (bottom-left "Open in Builder", bottom-right "Summary" — the builder's own floating pair, same geometry and colours) and `components/ProgramSummarySheet.tsx`, the read-only counterpart to the builder's Workout Summary: every cycle day with its exercise NAMES and nothing else, for "what's in this program" rather than "how is this day programmed". The builder pill is omitted where there's nothing to edit — a program sent TO you isn't yours until you accept it.
- **Dumbbell icon:** `components/DumbbellIcon.tsx` — the single canonical 3-path SVG. The variant inside `app/journal.tsx`'s local `WorkoutIcon` differs subtly in its `d` path and is intentionally left local until a pixel-diff confirms equivalence.
- **Liquid Glass:** only on functional surfaces (nav/tabs/modal chrome). Always guard with `isGlassEffectAPIAvailable()` + rgba fallback. Never set `opacity` on `GlassView` or its parents. `overflow: 'hidden'` on glass containers.
- **Animations:** Reanimated on UI thread. Haptics (`Haptics.impactAsync(ImpactFeedbackStyle.Light)`) on every primary tap.

## Workflow

- 3+ step or architectural work: short plan, confirm before building.
- Root-cause fixes, no patches. No hardcoded colors/insets.

## Shared utilities

Pure logic lives outside `app/` and `components/`. Reach for these before reinventing:

- `utils/dates.ts` — `parseStoredDate(s) → Date | null`, `toYMD(d) → "YYYY-MM-DD"`, `todayYMD()`, `fmtDuration(secs)`, `MONTH_NAMES`, `MONTH_FULL`. `parseStoredDate` is **strict** — it returns `null` on unparseable input. Callers MUST treat `null` as "no active program / no workout today" rather than constructing a January-year-0 fallback.
- `utils/storage.ts` — `getJSON<T>(key, fallback)`, `setJSON<T>(key, value)`, `removeKey(key)`. Use these in any **new** screen. Existing screens still call `AsyncStorage` directly; do not bulk-retrofit — each call site has bespoke ordering / rollback.
- `utils/workout.ts` — the **single source of truth** for resolving an active program's scheduled workout and for "previous values". `getTodaysWorkout(program)`, `getWorkoutForDate(program, "YYYY-MM-DD")` and `resolveTodayWorkout(program, override)` (honors a same-day change-day override) return `{ dayIndex, name, exercises, programId, dayId } | null` via the documented cycle math; `resolveDayIndex(...)` exposes just the index (pause-gated), `cycleIndexForDate(...)` the raw cycle math (used only by the dayId backfill). `buildPrevNotesByName(history, beforeDate?, day?)` is the same walk for the **"Last time" note hint** under an exercise's notes box: the note from the MOST RECENT session that included that exercise, so a session logged with no note BLOCKS an older one rather than being skipped (write a note in week 1, none in week 2, and week 3 shows nothing; week 1's note lives on in the journal). The hint is shown as the EMPTY box's placeholder — "Previous: …", greyed — and never pre-fills it, so an untouched hint carries nothing forward. A **Reuse** chip beside it puts the note in to keep or edit; once reused, the chip becomes **Undo**, which empties the box again until you type (then the text is yours). Both chip states are derived from the text, not stored, so a restored draft shows the right one. It lives in `components/ExerciseNotesField.tsx`, shared by workout and log-workout. `buildPrevByName(history, beforeDate?, day?)` builds the last-set-per-exercise map keyed by `normalizeExerciseName(name)` (trim + lowercase). `day` is a `PrevDayScope` built by `prevDayScopeFor(resolvedWorkout, sourceProgram)` — never assembled by hand, because it also resolves `absorbsUnidentified` against that program. With a scope the walk is **strict**: only sessions performed on that day count, matched exactly as `workoutMatchesDay` does (`dayId` + `programId`, name only for sessions that recorded no `dayId`, and then only onto the day that absorbs them). An exercise with no history on the day shows "—" rather than borrowing another day's numbers — two days called "Upper" read identically, so a borrowed figure is indistinguishable from the day's own. Screens MUST call these instead of re-implementing the cycle math or prev-set lookup inline.
- `utils/programDays.ts` — **day identity**. A workout day is identified by its `dayIds[i]` entry, never by its name: a cycle can schedule "Upper" twice, and a rename must not orphan the day's exercises or its logged sessions. `programDays(program) → ProgramDayRef[]` (one per training slot + extraWorkouts, **not** deduped by name), `dayIdAt(program, i)`, `indexOfDayId`, `normalizeDayIds(existing, length)` (grow/trim, keeping ids), `markDayRefLabels` (sets `absorbsUnidentified` / `duplicateLabel` across a scope), `historicalDays` (days reconstructed from sessions when the cycle no longer has them) and `forkChangedDayIds` (see "Editing a program that's already running"). Also owns the workouts-map key helpers — `workoutKey(i, label)`, `parseDayKey`, `dayLabel`, `trainingDayKeys`, and `canonicalizeWorkouts(map, names, isTraining)`, the rename-safe re-key pass every builder load/save path must go through.
- `utils/dayIdMigration.ts` — one-shot backfill (run from `app/_layout.tsx`, after the weight migration): fills `dayIds` on legacy programs and stamps `dayId` on history that predates it. See the module header for the attribution rules.
- `utils/streak.ts` — **when the app-open streak survives, freezes or resets**. `isStreakRiskDay(program, ymd)` is the whole idea: a day can only COST the streak if the active program schedules a workout on it, so Rest days and dates from `pausedAt` onward freeze it indefinitely. `missedStreakDays(program, lastOpened, today)` counts those risk days strictly between two opens (both ends are attended), and `streakSurvives(...)` is that count `<= STREAK_GRACE_DAYS` (1) — one missed workout day is free, the second ends the streak. With no active program (or an unparseable `startDate`, per the `parseStoredDate` rule above) every day is a risk day, so the buffer alone applies. `streakBreakDate(program, lastOpened, horizonDays)` returns the date the streak would end on if the app is never opened again; `notificationScheduler` schedules its single streak reminder for that evening and no other. Opening on a rest day still increments — rest days can't take the streak away, they just don't defend it.
- `utils/exerciseFavourites.ts` — starred exercises. Identity is the NAME (trim + lowercase, via `normalizeFavourite`), which is the handle the picker already selects and de-dupes on, so one list covers the catalogue and custom exercises. `isFavourite` / `toggleFavourite` (never mutates its input; re-starring under different casing removes rather than duplicating), and `sortByMuscleThenName` — the FAVOURITES block's order: muscle group in `MUSCLE_ORDER` (Chest, Back, Shoulders, Legs, Arms, Core), then alphabetical, with an unknown or missing muscle sorting last.
- `utils/weekSchedule.ts` — **Home's "This Week's Schedule" rows + the ring's counts**, and the reason Home and the Workout tab can't disagree about today. Three rules, each from a real report: (1) a LOGGED SESSION WINS over the plan, so a custom workout or a change-day swap landing on a cycle Rest day shows by name with its tick instead of reading "Rest"; (2) the effective day's row uses `resolvedTodayName` (what `resolveWorkoutForDate` gave the Workout tab, override and all), never the raw cycle; (3) "today" is `getEffectiveToday`, not the calendar day, so before 3am the highlight and the past/future line stay on the day the Workout tab is on. Every row is derived, so deleting a session takes its name and tick away on the next read. A day you TRAINED is not editable (marking it off would empty a date that still has a session). `scripts/verify-week-schedule.ts` covers the 1am log, the override swap, and complete → delete → redo.
- `utils/achievements.ts` — **what earns an achievement** (the compact cards under Recent Activity on Home, and the achievement notification; both come from here, never from a screen). PR = a strictly heavier top set on an exercise logged before (first-time logs, ties, 1RM and set-volume gains don't count). A session's PRs are ONE card holding every record in `prs` (heaviest first), not a headline plus a "plus N more" count: the card titles the number, names the exercises, and **expands** (`components/ExpandReveal.tsx`, shared with the Help & FAQ accordion) to list each one with a "View workout" link. Saying "plus N more" and navigating to the workout left the user to work out which lifts those were. Workout milestones 10/25/50/100/250/500, once each. Program = finishing one that reached its final week (Mark Complete early earns nothing; activating a new program over a finished one does earn it). Streak = app-open milestones, which can recur. Cards: one per category, newest replaces, gone after 7 days or when the workout that earned it is deleted. `utils/achievementStore.ts` is the RN side (storage + one notification per save, highest priority program > workouts > pr > streak). `scripts/verify-achievements.ts` covers the rules.
- `components/DumbbellIcon.tsx` — the canonical workout icon.
- `components/FavouriteStar.tsx` — the gold star, for anything favouritable. Owns the colour (`GOLD` / `GOLD_DARK`) and the glow, which is a TEXT shadow so it traces the glyph rather than the icon's square box, and is deliberately weaker on dark. `useFavouriteGold()` gives the matching colour for text set beside it.
- `utils/skippedDates.ts` — **what happens when a planned workout isn't done.** The user sees exactly two choices, and both keep their usual training days: **Make Rest Day** (that session is lost, nothing else moves) and **Move to Tomorrow** (it moves a day, the next rest day absorbs the shift, and the program still finishes on time). This replaced a three-choice prompt plus "tap a rest day to spend it", which were mechanically correct and impossible to tell apart — its "use Friday's rest day" button named an internal bookkeeping date while *Thursday* was the day that visibly changed. **The prompt describes results in days the user will see, never the mechanism**: `planDoItTomorrow` computes `lostRestDay` (the planned rest day that now holds a workout — not the pull date, which often stays a rest day) and `backOnPlan`, and `utils/restDay.ts` only renders those. "Move to Tomorrow" is stored as a push on the missed date **paired** with a pull on the next rest day; `unskipDate` on a push removes the first pull after it too, because an orphaned pull drags the rest of the program a day *early*. Pulls are never removed by date and never shown in the UI. Only a cycle with no rest day within one cycle yields a bare push (`kind: "extended"`), and only then does the program finish later. A skip and a pull may share a date (skipping the absorbing day must not un-absorb the move); a push and a pull may not. **"Set Workout Date" is a clean reset**: `clearShifts` runs before the offset solve, dropping every push and pull — past moves become plain skips so the calendar still reads rest, future moves are removed outright, plain skips are untouched. Without it the week looked back on plan while the finish date stayed however many days late.
- `utils/cycleDrift.ts` — **how far the program's timeline has slipped from the calendar**, and the reason the rest-day marks compose. A PUSH delays everything after it (+1 day, so the program finishes a day later); a PULL spends a rest day and brings everything from it forward (−1); a plain SKIP shifts nothing and just loses that session. The two ends are asymmetric and it is the whole off-by-one: a push INSERTS a blank day so it counts **strictly before** the date being resolved (it schedules nothing itself and must not delay itself), while a pull DELETES its date so it counts **from that date inclusive** (that day takes the following day's content). `cycleDrift` is a deliberately **dumb count** over two sorted string arrays — no cycle knowledge, no date parsing. Making the reader clever (checking at resolve time that each pulled date still lands on a Rest) breaks `app/programs.tsx:handleSetWorkoutDay`, which SOLVES for `cycleOffset` by computing the natural index with it zeroed; once the drift term depends on the offset that inversion is invalid, measured at 4 of 6 target days landing on the wrong date. The "a pull must sit on a Rest" invariant is enforced on the WRITE side by `normalizeDriftDates` (`utils/workout.ts`) instead — **every path that persists a program must run it**, exactly like `canonicalizeWorkouts`, and for the same reason: a stored date silently invalidated by a neighbouring edit. It re-targets a stale pull to the next rest day rather than dropping it, so the user's "I want that day back" survives. Re-activating or duplicating a program clears all three lists: every mark predates the new `startDate` and would otherwise count as drift against day 1.
- **Day arithmetic rounds, never floors.** `Math.floor((a - b) / 86400000)` on two local midnights drops a whole day across a daylight-saving transition (a 23-hour day), which shifted the cycle one slot early for every date between the spring and autumn transitions. `utils/dates.ts:daysBetweenYMD` has always rounded; `cycleIndexForDate` and `getCurrentWeek` now do too, and `scripts/verify-skipped-dates.ts` walks 400 consecutive days asserting the cycle advances by exactly one slot per day, which fails in any DST zone if this regresses.
- `constants/programs.ts:getCurrentWeek(program, today?)` / `programFinishDate(program)` — the week counter is measured against the program's own timeline, not the calendar, so a pushed day holds the WEEK still as well as the cycle; otherwise the two drift apart and the program quietly loses a day of programming off the end per push. `programFinishDate` is a **fixed point, not a formula** (pushing the end out can bring further marks inside the window, which push it out again) — do not "simplify" the loop away.
- `constants/cards.ts` — the geometry a card shares with its one-line summary row. Any section that can be shown as full cards OR as a compact list renders the SAME title through two different trees, so the two must agree or the title jumps when the section is toggled. The contract: a title's box sits exactly `CARD_PAD` below the card's inner top edge and `CARD_PAD` in from its left edge, at `CARD_TITLE`'s size and line height — which is why `SUMMARY_ROW`'s vertical padding is `CARD_PAD` rather than something tuned to look compact on its own. `CARD_TITLE_LINE` and `CARD_PILL_H` are equal on purpose: a summary row is `alignItems: "center"`, so a status pill even a point taller than the title would centre the title downward in list mode and nowhere else. Use `CARD_INNER` / `CARD_TOP` / `CARD_TITLE` / `CARD_META` on the card and `SUMMARY_ROW` / `CARD_TITLE` on the row; never re-tune the numbers per screen.
- **Chat messages (1:1 and group)** — tapping a bubble (`ChatBubble`'s `onPress`, the bubble not the full-width row) opens that chat's ONE `SimpleSheet` on a `message` step (`components/trainer/MessageActions.tsx`): your own → **Delete message**, someone else's → **Report message**, which moves the same sheet on to `ReportReasonList`. Every chat interaction (menu, pick a person, message, reasons) is a step of that one sheet, never a second modal. Deleting is a SOFT delete through migration 0031's `delete_message` / `delete_group_message` RPCs (sender-only, no UPDATE policy, so nobody can edit what they said): the server blanks the body and stamps `deleted_at`, the row stays so the thread shows "You deleted this message" / "Message deleted by …" in place, `previewText` (`utils/chatStore.ts`) says so in both conversation lists, and `countUnreadInThread` never counts one. The realtime subscriptions listen for UPDATE as well as INSERT so the other side sees it live. A group OWNER's reported-message removal is separate and still a hard delete (`deleteGroupMessage`). **Message reads are newest-first**: the API caps a read at 1000 rows, and every message fetch in `lib/chat.ts` / `lib/groups.ts` used to ask oldest-first, so past that the cap dropped the NEWEST messages, which is what previews and unread badges are built from (every group badge sat at 0). Order descending and reverse in memory; never `ascending: true` on a message list. The group page's badge reads `loadGroupUnread(groupId)` (just that group, since the read stamp), and **a group read stamp is the newest loaded message's `created_at`** (server time), not the phone's clock, because unread is decided by comparing against server timestamps. Realtime channel names carry a per-call counter: `supabase.channel(name)` returns a still-closing channel of the same name, whose new listeners never fire.
- `constants/groups.ts` — group types, `canCoachGroup(role)`, and the group-chat key helpers. Since migration 0027 a `group_members` row means **invited**; `accepted_at` is what makes it a membership, and every "is this person in this group?" question routes through the database's `is_group_member()`, so a pending invitee is out of the thread, the roster and the read stamps without any screen having to check. A group can carry a **photo** (migration 0030): `groups.avatar_url` holds a public URL, the image lives at `group-avatars/<groupId>/avatar`, and only the group's OWNER may write it — the bucket is separate from `avatars` because that one pins the first path segment to the caller's uid, and a group's photo belongs to the group. Every surface draws it through `components/trainer/GroupAvatar.tsx`, which falls back to the accent-tinted people icon, so a group without one looks exactly as it did before. A new group's photo can only upload AFTER `create_group` returns an id, so `group-edit.tsx` stages the pick and commits it on Save. Membership is **role-blind**: `create_group` / `set_group_members` ask for an accepted connection and nothing else, so a fellow TRAINER joins a group exactly like a client does (and can then be promoted to coach it). `app/trainer/group-edit.tsx` therefore builds its picker from BOTH roster buckets — it used `clients` alone, which meant a trainer had to be taken on as a client first. `GroupInvite` is deliberately thin — it comes from `get_my_group_invites()`, not from the group row, and is the whole of what someone may know about a group they haven't joined. A group program send still goes to EVERY invited member so it's waiting for them on accept.

### Programs in a group — two directions, one table

Both are `shared_programs` rows carrying a `group_id`; `kind` and row count are what separate them. **`group_id` is also the whole of the "does this belong to the group" test** — a direct send to one trainer has `group_id = null` and therefore cannot appear on a group page, which is exactly the guarantee the group screens rely on.

| | `kind` | Rows | `recipient_id` | Who acts |
| --- | --- | --- | --- | --- |
| Coach → group ("Programs Sent") | `share` | one per invited member | each member | sender + any coach may delete; each member accepts their own |
| Member → group ("Programs Received") | `review` | **one** | the group's owner | any coach reviews, sends back, and Removes (clears the queue) |

**Removing a group send is always the whole send** (`removeGroupSharedProgramBatch`), from the group page's card AND the program view's bin, and for the sender as well as any coach, whatever the sender's role is now. Never `removeSharedProgram` on a group row: it only knows "I sent it" vs "I received it", so an owner removing another trainer's send only hid their own copy, and a sender took out one member's copy of many. It throws when nothing it matched was deleted (a refused delete is a silent no-op to the API), and the screens show that as an alert rather than a dead button.

A review is one row on purpose: it's a queue item, not a request for N second opinions, and N rows would mean N returned snapshots of one program with nothing to say which the member should follow. `recipient_id` is the owner only because the column is `NOT NULL` — `coaches_group()` decides who may act. That's why `loadGroupReviewPrograms(groupId)` exists: `loadSentPrograms` would only ever surface it to the owner, so any screen opening a group review passes `groupId` through to the review screen, which looks it up through the group's queue instead of an inbox.

**Three reads of the same rows, and which one a screen wants depends on how it's scoped.** `loadSentPrograms` is scoped by ADDRESS (`sender_id` / `recipient_id`), so it can't see a group review unless you're the owner — hence `!r.group_id` there, which stops the owner's hub becoming every group's backlog. `loadGroupReviewPrograms(groupId)` is one group's open queue, for that group's page. `loadMyGroupReviews()` is every open group review I'm entitled to, gathered for a coach's hub so they don't have to open each group to find work in it; it's scoped by the `shared_programs_select` POLICY rather than by the address, and drops rows I sent myself. A coach therefore sees a group review in both places — its group's page and their hub's **Programs Received**, beside the 1:1 ones — and can review or Remove it from either. Both places use the same card — a white **Edit & Send Back** (or **View Review** once returned) and a red **Remove** — and on the trainer hub Remove means different things by source: a GROUP review is cleared from the group's queue for every coach (`setGroupReviewDone`, what "Mark Done" used to be), a 1:1 review is hidden from that trainer's inbox only (`dismissReceivedReview` stamps `deleted_by_recipient_at`, which `loadSentPrograms` already filters). The review screen puts **Send Back** directly under the program's name: after it started showing the full program, a button at the foot of the page was a long scroll away and read as missing.

For the SENDER, a review splits across their trainer page by state: still waiting → **Sent to Trainer**; returned → **From Your Trainer**, among received programs, labelled "You sent this for review", with View · Accept (apply the changes) · Remove (a local hide keyed by `sentKeyOf`, in the same dismissed list as received programs).

The sender sees their own request too, on the group's page under **Sent to Trainer**, with no actions. **Who can send, who can ask** (`canSendToGroup` on the group page): **Send Program** is for the owner and for TRAINER ACCOUNTS the owner has made trainers; a trainer account also gets a white **Ask for Review** on its own row. Everyone else (every member, and a GYM USER whatever their role) has **Ask for Review** as their one green button and can never send a program out to the group; a gym user's role still lets them review and remove as a coach. A member's view leaves out their own sends (from a time they were a trainer): those stay in the group for everyone else, but a member has no Programs Sent, and "From Your Trainer" would mislabel them. With Send Program only, a client given the trainer role sent their program OUT to the group when they meant "review this", and it landed in Programs Sent. Because a trainer can now be on both ends, the group page splits the queue by sender (`receivedReviews` vs `myReviewRequests`): nobody's own request appears in their Programs Received with review actions on it. (A group page names its two program sections from where the reader stands: a coach sees **Programs Received** / **Programs Sent**, as on the trainer hub; a member sees **From Your Trainer** above **Sent to Trainer**, the names and the order of the gym user's trainer page. The two are `sharesSection` / `reviewsSection` in `app/trainer/group/[id]/index.tsx`, rendered in an order chosen by `iCoachGroup`.) A gym user tracks it on their own trainer page as well; a TRAINER who is a plain member of someone else's group has no such list (their hub holds reviews addressed to *them*), so the group page is the only place it exists for them.

Clearing the queue is `completed_at`, written only through `set_group_review_completed` so a sender can't close their own review — it drops the item from the group and from every coach's hub, and leaves the member's copy untouched.
- `constants/programs.ts`, `constants/journal.ts`, `constants/exercises.ts` — storage keys + shared types live here. Do not hardcode storage keys in screens.

### Active program → today's workout

1. Read `@avenas/programs`; find the entry with `status === "active"` (there's at most one).
2. `daysPassed = floor((midnight(today) - midnight(parseStoredDate(startDate))) / 1 day)`.
3. `dayIndex = (((daysPassed + (cycleOffset ?? 0)) mod cycleDays) + cycleDays) mod cycleDays` — handles negative results correctly.
4. `dayName = cyclePattern[dayIndex]`. If it's `"Rest"` or empty → no workout today.
5. `workoutKey = ${dayIndex}:${dayName}`. Exercises = `workouts[workoutKey] ?? []`.

The `:` in `${i}:${name}` is the separator between index and label. The matching `dayLabel` helper splits on `:` and rejoins with `slice(1).join(":")`, so a name containing `:` round-trips correctly — but prefer to avoid it.

### Day identity — a name is never an identity

The label in a workout key is decoration; the **index** makes the key unique, and `dayIds[index]` is what identifies the day to everything outside the program. Two consequences, both load-bearing:

- **A rename changes every key on that day.** Any path that rebuilds the builder's `WorkoutMap` MUST go through `canonicalizeWorkouts(map, names, isTraining)` (`utils/programDays.ts`), which carries exercises across by index. Looking the new key up directly resolves to `undefined`, and the `?? []` behind it deletes the day's exercises — that was a real data-loss bug across four separate load paths.
- **A cycle may schedule the same name twice.** Never `cyclePattern.indexOf(name)` to find a day, never dedupe a day list by name, and never match history on `workoutName` when a `dayId` is available. Use `programDays(program)` for lists and `indexOfDayId` for lookups; the Progress page matches sessions with `workoutMatchesDay` (`utils/progressStats.ts`), which prefers `dayId` and only falls back to the name for records that have none — and then only onto the day marked `absorbsUnidentified`, so an ambiguous record is counted once rather than on every same-named row.

### Editing a program that's already running

Logged history is a **snapshot and is never rewritten**. `CompletedWorkout` carries its own `exercises` and `workoutName`, and the Journal + workout-detail render those, so editing a program can't retroactively change what a past session says — same contract as swapping an exercise mid-session on the Workout screen. Only sessions logged *after* the edit use the new programming.

What the edit does change is how the Progress page groups things, decided entirely by whether the day's `dayId` survives the save (`forkChangedDayIds`, applied in `new-program.tsx:handleFinish` against `originalEdit.current`):

| Edit | `dayId` | Progress |
| --- | --- | --- |
| Day moved to another cycle slot | kept (ids permute with the day) | unchanged — the page doesn't care which cycle day a session fell on |
| Renamed only | kept | one row, relabelled; the pre-rename sessions stay on it |
| Exercises swapped only | kept | one row; the dropped exercise still lists, flagged `inProgram: false` ("Swapped out") |
| Renamed **and** exercises changed | **new id minted** | two rows: the replacement, plus the old day as a historical row |
| Day deleted from the cycle | leaves `dayIds` | its sessions become a historical row |

"Exercises changed" compares the SET of exercise names — editing sets, reps, weight or rest is programming, not a different workout, and must not fork.

Historical rows are **derived from history, not stored**: `historicalDays` reconstructs any `dayId` that has sessions but no longer exists in an in-scope program's cycle, labelling it from the most recent session's `workoutName`. They carry `isHistorical: true`, an empty `programExercises` (nothing on them can read as "swapped out" — there's no current prescription), and never absorb unidentified sessions ahead of a live day.

### Override (change-day) flow

`@avenas/today_workout_override` stores `{ date, workoutName, programId?, dayId? }`. Honor it only when `override.date` matches the effective day — stale overrides from a previous day must be ignored. Resolution goes through `resolveWorkoutForDate(program, override, dateYMD, allPrograms?)`: the day is looked up in its **source** program (`programId`, which change-day records because the user can pick a day from a non-active program), falling back to the active program when `programId` is absent (legacy override / free workout) or its program is gone. Pass the full `allPrograms` list or cross-program overrides degrade to name-only. Inside that program the slot is found by `dayId`; the `indexOf(name)` fallback (legacy / free-workout overrides) always lands on the first day of that name. A day resolved by id surfaces its CURRENT label, so a rename since the override was written shows the new name. The override key is also used by the "free workout" flow to remember the user-chosen name across reloads (no `programId` / `dayId`).

### Save flow — what triggers Home / Journal updates

When the user taps **Finish** on a workout, in order:

1. Build a `CompletedWorkout` synchronously in memory (so the locked completed view can be set on the same tick), stamping `programId` and `dayId` from the resolved workout.
2. Set `setTodaysCompletedWorkout(completed)` synchronously.
3. `await` a sequential pair of `getItem → setItem` against `@avenas/workout_history` to prepend the workout. Sequential awaits prevent rapid back-to-back finishes racing.
4. `await` the same pattern against `@avenas/workout_dates` to ensure the date is recorded once.
5. Refresh in-memory `prevByName` from the newly-written history so a same-session discard-and-restart gets correct previous-set suggestions.
6. Clear `@avenas/workout_draft` and stop the workout timer.
7. If `isFreeWorkout && addToProgram && activeProgram` is true, append the workout name to `activeProgram.extraWorkouts` in `@avenas/programs`.

Home and Journal pick up the new workout on their next `useFocusEffect`. They are read-only with respect to workout history (Journal can additionally delete journal entries, never workouts directly).

### Edit-flow change detection

`new-program.tsx` shows the "Update" button and the "Unsaved Changes" navigation prompt based on whether the working draft differs from `originalEdit.current`. **Both** surfaces must agree, so they call the same `workoutsEqual(a, b)` helper. The `WorkoutMap` comparison uses a sorted-keys JSON form because object-key insertion order is not significant.

## Conventions for new screens (e.g. the upcoming Program Page)

A new screen plugs into the contract by following these rules — break any of them and the four interlinked pages start to drift:

- Use date helpers from `utils/dates.ts`. Do not inline `MONTH_NAMES` arrays or hand-rolled `parseStoredDate`.
- Use `utils/storage.ts:getJSON/setJSON` for new persistence paths.
- Use `<DumbbellIcon />` from `components/`.
- Storage keys come from `constants/programs.ts` and `constants/journal.ts`. Do not hardcode key strings.
- Treat `parseStoredDate(...)` returning `null` as "no active program / no workout today". Never fall back to month 0.
- Identify a workout day by its `dayId`, never by its name — see "Day identity" above. Lists of days come from `programDays(program)`; lookups from `indexOfDayId`; history matching from `workoutMatchesDay`.
- For `WorkoutMap` equality checks, use the sorted-keys form (see `workoutsEqual` in `new-program.tsx`). Plain `JSON.stringify` is order-sensitive and will produce phantom diffs.
- Never block the UI on a `setItem`. Optimistic-update + rollback-on-failure is the established pattern (see `journal.tsx:saveEntries`).
- Storage errors → `if (__DEV__) console.warn("[avenas]", op, key, err)`. Do not surface as user-facing Alerts (that would change behavior).
- When mutating shared keys (`workout_history`, `workout_dates`, `programs`), serialize the read→write pair with sequential `await`s. Never `getItem(...).then(setItem(...))` without an `await` in between — that pattern races concurrent writers.
