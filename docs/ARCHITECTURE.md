# Avenas: architecture and decisions (full reference)

The detailed record behind `CLAUDE.md`. Not loaded automatically: read the section for whatever you're changing. When a rule here changes, update it here, and add or edit its one-liner in `CLAUDE.md` only if it's a rule that's easy to break.

iOS-first React Native + Expo (SDK 58, RN 0.88, React 19.3, New Architecture), TypeScript strict. Expo Router; the tabs are Apple's own tab bar (`NativeTabs`) on iOS 26 and later, the app's own below that and on Android. Shipped to App Store.

## Non-obvious rules

- **StyleSheet only** — no Tailwind, no styled-components.
- **Packages: `npx expo install`**, never `npm install`. This tree resolves with `--legacy-peer-deps` (an optional `react-native-windows` peer on `@react-native-community/datetimepicker` otherwise fails resolution), so pass `-- --legacy-peer-deps`.
- **Never import `@react-navigation/*`** — expo-router dropped react-navigation in SDK 56 and importing it fails the bundle. `useFocusEffect` and friends come from `expo-router`.
- **`StyleSheet.absoluteFill`**, not `absoluteFillObject` — the latter was removed in RN 0.86.
- **SDK 58 (upgraded 2026-10-28, because Expo Go only runs the latest SDK).** Its changes, each a rule now: (1) **RN 0.88's strict TypeScript API**: a component's name is no longer its instance's type, so refs take `TextInputInstance` / `ScrollViewInstance` / `ViewInstance` (`useRef<TextInput>` lost `.focus()`, `useRef<ScrollView>` `.scrollTo()`), and `NativeMethods` is gone for `HostInstance`. (2) **`components/MaskedView.tsx`** re-exports the package's view with its props typed again: masked-view 0.3.2, its latest, builds its type on `NativeMethods`, which broke every `<MaskedView>` (the blurred top of ~39 pages) as a JSX component; an augmentation of `react-native` restoring the name didn't take. Import it from there, and drop the wrapper once the package ships RN 0.88 types. (3) **expo-router 58 reworked its navigation core**: the `beforeRemove` event is gone, so the builder's "Unsaved Changes" guard is `usePreventRemove` (its `leaving` state, `leaveSaved()` standing it down before a save's `router.back()`; left on the old listener it would never have fired), and a custom tab bar gets `navigateToTab(route.key)` instead of `navigation`. (4) **expo-file-system's `File.write()` is async**: the CSV export awaits it before sharing (unawaited, the share could send an empty file). (5) **expo-image no longer takes RN's `ImageSourcePropType`** (it allows a readonly array now), so the exercise image maps are typed `number`, what a bundled `require` is, in `scripts/build-exercises.mjs` and its output. (6) **The iOS scene life cycle**: the window is the scene's, so `AvenasAppearanceAppDelegateSubscriber` finds it through `Utilities.keyWindow()` (the app delegate's window only as a fallback); Expo forwards the scene's becoming active to `applicationDidBecomeActive`. Also: gesture-handler went to 3 (only a dependency of expo-router and screens; the app never imports it), Android release builds minify with R8 by default, notifications show in the foreground unless `setNotificationHandler` says otherwise (ours always does, by category), and `web.output` stays `"static"`.
- **Changing an exercise for another: `ExercisePicker` with `changing={oldName}`** (title "Change Exercise", "REPLACING …", one pick, "Swap Exercise"), on every change flow: the builder, the Workout tab, log-workout, workout-detail. Without it the sheet said "Add Exercise", took numbered multi-picks and kept only the first. In the builder (user request, 2026-10-13) every row of the reorder sheet and the Workout Summary has a **Change** pill (a tap on the name does the same), and `swapExercise` changes the name ONLY: sets (warm-ups, targets, ranges), rest, Hold and notes stay, and so does the id, so the exercise keeps its place in the day; another program's carried details for the old name go. A trip to create a custom exercise mid-swap comes back to the swap (`pendingPicker`).
- **Picking a photo or video: `lib/photoPicker.ts:pickFromLibrary`**, never `ImagePicker.launchImageLibraryAsync` from a screen. No permission request first (the system picker needs none; asking put a prompt in its way and locked out anyone who'd said no), one picker at a time, and `afterAlert` when opened from an Alert button (iOS drops a picker presented while the alert is still closing). A photo's circle and its "Tap to add" caption are one touchable.
- **A field being typed into ends clear of the keyboard and its tools** (the floating down key, a page's ‹ › arrows: `ABOVE_KEYBOARD_TOOLS` in `constants/floatingBars.ts`), on every scrolling page (user report, 2026-10-13: notes on the Journal's workout page stayed behind the keyboard). A plain form uses `KeyboardAwareScrollView` from react-native-keyboard-controller with `bottomOffset={ABOVE_KEYBOARD_TOOLS}` (Profile, sign-in and sign-up, Connect, Report a Bug, Request a Feature, Create Exercise). A page whose content animates its own height (`CollapsibleCard`, `ExpandablePanel`: the Workout tab, log-workout, workout-detail) keeps a plain `ScrollView` in a `KeyboardAvoidingView` and reports each LIST field's focus to `hooks/useFieldAboveKeyboard.ts`, which scrolls that field clear as the keyboard opens and as focus moves with it up (a tap, the ‹ › keys), and only that far; `KeyboardAwareScrollView` is a Reanimated.ScrollView, which doesn't reflow for those animations. A field outside the list (a floating notes card, a sheet) never reports. The builder keeps the iOS `automaticallyAdjustKeyboardInsets`, which only scrolls as the keyboard opens and only to its top edge. A KeyboardAvoidingView around a plain ScrollView alone shrinks the list but never moves the field, which is what left fields hidden.
- **Lists:** `FlashList`. **Images:** `expo-image`. **Secrets/tokens:** `expo-secure-store` (not AsyncStorage).
- **Colors:** `constants/theme.ts` (`ACCT`, `APP_LIGHT`, `APP_DARK`, `NEU_BG`) — no hex literals in screens. **Lines use `t.div` in both themes** (dividers, hairlines, borders, chart `rulesColor`/`xAxisColor`, quiet fills): dark's is a translucent white, so it lifts off cards and the page alike. It was a solid navy identical to the card colour, which made every dark-mode line invisible and bred ~32 `isDark ? "rgba(255,255,255,0.1)" : t.div` workarounds; don't reintroduce that idiom. **Two reds, by job:** `DANGER_BRIGHT` for anything that deletes, removes or discards (fills, trash icons, red Delete/Remove labels), `DANGER` for warnings and block/report. There used to be three different delete reds. **Green words on a light card use `accentTextColor(isDark)`** (`ACCT_INK`, a deeper green; user decision, 2026-10-14): `ACCT` as text reads at about 1.5:1 there. Marks (bars, lines, dots, fills, glows) stay `ACCT`, dark mode keeps `ACCT` for words too, and orange words split the same way (`replacedTextColor`). The Progress page's tapped totals and Sets block reps go through it; a pop-up on the near-black tooltip keeps `ACCT`, and so do **the page's gains** (the exercise chart's "▲ 18%" and the radar's ▲), in the same green as the comparison page's (user decision, 2026-10-16, reversing the 14th's deeper green for them). **While comparing two programs, the green program's numbers and words are plain `ACCT`**, matching its dot (user decision, 2026-10-14, after seeing the deeper green beside it), all but the reps written on its pale Sets blocks, which keep `accentTextColor` (bright green on a pale green block reads at about 1.2:1).
- **The app's look is Porcelain (light) and Graphite (dark)** (user picks, 2026-10-28: option C of the Light Mode Whites canvas and option B of the Dark Mode Home canvas; tried on Home first behind a switch, then rolled out to every page, sheet, the lock screen card and the launch screen the same day, and the switch removed). Porcelain: a pale cool page (`APP_LIGHT.bg` `#EDF1F6`), white cards (`NEU_BG`) with a soft, wide, cool shade down-right (`CARD_SHADE`) and a white glow up-left (`CARD_GLOW`), and greys dark enough to read on white. Graphite: a near-black page (`APP_DARK.bg` `#111214`), charcoal cards (`NEU_BG_DARK` `#1C1D21`) with a faint white edge (`CARD_EDGE_DARK`) and a plain black drop shadow (`CARD_SHADE_DARK`) where the navy cards had a 20% white rim, and lighter greys. They replaced a grey-blue neumorphic look and a navy one. **Anything raised by hand (not a `NeuCard`) takes these tokens**, never a shadow hex: the old `#a3afc0` shade and navy steps (`#343759`, `#2e3555`) were hard-coded in a dozen places and had to be found one by one. A set's input boxes on dark are `SET_INPUT_DARK`. The quick-action orbs (`ORB_GRADS`: New Program sky to mint, My Programs ocean blue, View Journal periwinkle to orchid) are their canvas colours pushed to their most saturated: the canvas's values looked very dull on the phone, which draws sRGB exactly where a wide-colour monitor saturates it. The lock screen card (`targets/workout-widget/index.swift`, `CardPalette`) and the launch screen (`app.json` splash) carry the same colours, so they only change with a native build.
- **A button's coloured glow is softer on dark** (user report, 2026-10-28: on Graphite's near-black the green and red glows read "a little too bright and glowy", which light mode doesn't show). `constants/buttons.ts`: every button glow is laid on at `DARK_GLOW_SCALE` (0.6) of its light-mode strength on dark, one number to tune. Three ways in, by where the glow is written: `pillGlow(color, opacity, isDark)` / `haloGlow(color, opacity, radius, isDark)` inline; `glowOpacity(x, isDark)` for a `shadowOpacity` written by hand; `darkGlow(styles.x, isDark)` laid after a stylesheet entry that carries the glow (a stylesheet can't know the theme). It covers buttons and controls (pills, round add / remove / tick buttons, selected chips and toggles, the set checkboxes, the orbs, sheet pills, the glass buttons' solid fallback), not marks: progress segments, calendar days, rings, dots, badges and the decorative ticks keep their glow. **Not by colour:** an iOS dynamic colour on `shadowColor` looked like a one-place fix, but Fabric resolves `layer.shadowColor` once when the prop is set and doesn't re-resolve it on a trait change (`RCTViewComponentView invalidateLayer`), so a live theme toggle would leave stale glows.
- **The app's theme reaches native code too** (`contexts/ThemeContext.tsx`, `modules/avenas-appearance`). The app follows its own Dark Mode switch, never the phone's, but the splash, alerts, the keyboard and menus are drawn natively and followed the PHONE: a phone in dark mode opened a light app on a dark splash (user report and decision, 2026-10-11). Once the saved theme is read, ThemeContext calls `Appearance.setColorScheme` (what's on screen now) and `saveLaunchTheme` (the next launch), and the splash stays up until that read. iOS draws its launch screen before any app code runs, from Info.plist, which `modules/avenas-appearance/app.plugin.js` sets to Light; it must stay listed BEFORE expo-splash-screen in app.json, which sets Automatic whenever a dark splash is configured (the plugin listed later runs first, so the earlier one has the last word). `AvenasAppearanceAppDelegateSubscriber` then fades a saved Dark Mode in once the first frame is up, so a dark user sees white for a moment first, which nothing in the app can avoid. Android 12+ keeps it as the app's own night mode (`UiModeManager.setApplicationNightMode`), which its splash is drawn in; before 12 the splash follows the phone. Native code: none of it shows in Expo Go.
- **Safe areas:** `useSafeAreaInsets()` — never hardcode inset values.
- **The tab bar is Apple's own on iOS 26 and later, the app's below that and on Android** (user request, 2026-10-16: Bevel's bar, which bounces up under a press, stays up while held and slides between tabs, all of it Apple's tab bar's own; `NATIVE_TAB_BAR` in `hooks/useTabBar.ts`, picked once per launch in `app/(tabs)/_layout.tsx`, `expo-router/unstable-native-tabs`, in Expo Go). Inside Apple's tabs, Expo Router gives each page a safe area that takes the bar in, so **every tab page's default export goes through `tabScreen()`** (`components/TabScreen.tsx`): it gives the page back the window's safe area, which its own end padding and every sheet opened from it were laid out for (otherwise each counts the bar twice), and reports where the bar is. A fifth tab needs it too. **Anything that stands on the tab bar takes its place from `useTabBar()`** (`top`, `clearance`, `aboveRest`, `hideY`; the formulas are `tabBarClearance` / `aboveRestOnTab` / `barHideY` in `constants/floatingBars.ts`), never a fixed height: the app's bar's top edge is `NAV_BAR_TOP` (92), Apple's is measured (83 on a Face ID iPhone). Read them as the hook's numbers, not worked out on the page: React Compiler takes a function's result as possibly mutable, and `tabBarClearance(top)` inside the Workout page's focus-row closure made it skip optimising the whole screen. Apple's bar never shrinks on scroll (the floating bars stand on it), pages keep their own end padding (`disableAutomaticContentInsets`), every tab press gives the light haptic, and a second tap on Workout doesn't scroll it to the top. **Its icons are the app's own** (user decision, over SF Symbols): drawings in `constants/tabIcons.ts`, drawn by `components/DrawnIcon.tsx` on the app's bar and rendered to images for Apple's (`assets/images/tab-icons/`, template images iOS tints), so after changing a drawing run `npx tsx scripts/build-tab-icons.ts`. Labels in Nunito, black or white through `PlatformColor("label")`, which turns with the glass as it goes light or dark over the page, with Apple's highlight and a semibold label marking the selected tab (never iOS blue).
- **A tab page's title is set as Home's greeting** (user decision, 2026-10-21): 28pt bold, 20pt in (level with the cards), at `insets.top + 50`, and as the person typed it, never in capitals. The Workout tab's day name was in capitals with letter spacing and Progress's title was 32pt at 24pt, so the three read as different headers. The Trainer tab's title is the tab's own name, "Trainer" (`components/trainer/HubTitle.tsx`, on both hubs), and scrolls with the page. On a trainer's hub its buttons sit on the title's row, on its right, as Progress has Compare: the labelled "My Trainers" pill (`MyTrainersPill`) and Messages (see "The trainer's Trainer tab" below). On a gym user's hub the pill stands there alone (see "a gym user's Trainer tab" below). Pinning the buttons over the page (`HubTopBar`) was tried on both on 2026-10-21, turned down, and is gone.
- **Nothing on the way to Home waits on the server** (user report, 2026-10-14: a phone with no signal sat loading and never got into the app). The splash waits only on reads off the phone (theme, profile, the saved sign-in), and every server call at launch runs in the background. Two used to wait. (1) **Who's signed in** came from `supabase.auth.getSession()`, which renews a token over an hour old before answering: with no signal it retried for up to 30s, then answered "no session" with the sign-in still saved, and the app sent a signed-in person to onboarding. `contexts/AuthContext.tsx` now opens on the session saved on the phone (`readSavedSession` / `AUTH_STORAGE_KEY` in `lib/supabase.ts`, supabase-js's own default key named explicitly; the rules in `utils/savedSession.ts`), whatever its token's age, and follows supabase-js's events from there: a renewal replaces it, only `SIGNED_OUT` ends it, and a null `INITIAL_SESSION` (supabase-js failing to renew offline) changes nothing. supabase-js renews the token every 30s while the app is open and before every request, so the session in context can hold an expired token offline: take a token from `getSession()`, never from `useAuth()`. A `SIGNED_OUT` this phone didn't ask for is the server ending the sign-in (signed out on another phone, which signs out every device, or the account deleted): `endedElsewhere` counts it and `app/_layout.tsx` goes to onboarding with an alert. So **every sign-out goes through `signOutHere()`** (`lib/supabase.ts`), which also works offline: supabase-js signs out on the server first and, when it can't, KEEPS the session, so the saved copy is removed and a local sign-out finishes it. (2) **The update gate** (`components/ForceUpdateGate.tsx`) put a spinner in place of the app until `fetchMinIosVersion()` answered. It now decides from the last minimum the server gave (`MIN_IOS_VERSION_KEY`, `lib/appConfig.ts`) and asks the server in the background, so the one launch after the minimum is raised shows the app for a moment before the gate (the plan the user approved, 2026-10-15). **A backup that can't go is owed** (`BACKUP_OWED_KEY` in `lib/cloud.ts`): every `scheduleCloudPush` sets it, only a push that went through with nothing changed since it began clears it, and `pushOwedBackup` sends it 2s after launch and when the signal comes back (leaving the app pushes anyway); Data & Sync says "Waiting to back up" meanwhile. Before, the retry lived in memory, so a workout logged offline with the app closed before the signal came back reached the cloud, and a trainer, only with the next change. A push whose `getSession()` errs is `"failed"`, never `"skipped"`: as a skip it was never retried and let a sign-out past its backup check. A workout in progress never needed the server: the Workout page writes its draft at most 400ms after a change and at once when the app is left, the Journal's log writes on every change, and the timer on every start and pause, so a phone dying loses at most the last moment, and a session whose day is over before it's opened again goes to the Journal unfinished rather than being dropped (`utils/heldSession.ts` entry). `scripts/verify-offline-launch.ts` runs the real auth library offline on a fast clock, and the real `lib/syncManager.ts` across restarts.
- **Forgot Password is a CODE, never a link** (`app/forgot-password.tsx`, `lib/auth.ts`; 2026-10-14): Supabase emails a reset code (`resetPasswordForEmail`; the dashboard's Reset Password template must show `{{ .Token }}`), the code signs in (`verifyOtp` type `recovery`) and `updateUser` sets the password. A link signs in only on the phone that asked (PKCE), never opens in Expo Go, and points at the stale Site URL. A recovery sign-in fires `PASSWORD_RECOVERY`, not `SIGNED_IN`, so `contexts/AuthContext.tsx` treats both as a sign-in (otherwise the account's data never loads). Real users need custom SMTP in the dashboard: the built-in sender only mails the project's team. **The log-in screen's link is hidden (`PASSWORD_RESET_READY` in `app/login.tsx`) until the domain, Resend and the template are in** (user decision, 2026-10-14); flip it then.

## Components to reuse

- **Cards:** `NeuCard`. **Buttons:** `BounceButton` (primary = `ACCT` bg + `ACCT` shadow glow). **A NeuCard of a fixed size inside something that sizes to its content (a `BounceButton`, a row) gets its size from its CHILD** (a sized view inside it, 2pt under the size for the clip layer's edge), never from `fill` + `style`: `fill` is `flex: 1` on all three layers, which takes the parent's height, and a parent sized by its content has none, so the card draws at zero height, silently (the Workout timer's ±15s and Reset, user report 2026-10-15). `fill` is for a parent with a definite size.
- **A delete on a row or card:** `components/DeleteCircleButton.tsx`, the red circle with a white bin and red glow (`DANGER_BRIGHT` + `haloGlow`, `DELETE_CIRCLE_SIZE` 32, the picker's size), The builder's reorder / Workout Summary rows use it (user request, 2026-10-13), beside the Change pill, which is `DELETE_CIRCLE_SIZE` tall so the pair lines up; the builder's exercise CARD keeps its plain red bin icon (user decision, the same day, after seeing the circle there). The caller still asks before deleting.
- **Back button:** `components/BackButton.tsx` on every pushed screen, never a hand-built chevron. It owns the one position (`BACK_TOP` 16 below the top inset, `BACK_LEFT` 20, `BACK_SIZE` 40) and the haptic; `inline` for a header bar, whose row then pads by `insets.top + BACK_TOP` / `BACK_LEFT`. A title beside it is centred on it by construction: its row starts at `insets.top + BACK_TOP` and is `BACK_SIZE` tall, and a button on the right sits at the same `BACK_TOP`. It had drifted to four positions across ~35 screens.
- **Buttons in a sheet:** `components/SheetPill.tsx` — the pill from `constants/buttons.ts` in four treatments: `default` (control surface, a choice), `primary` (accent, the sheet's main action), `danger` (red fill, Delete / Block / Leave), `cancel` (Cancel: the slate button, `BTN_SLATE` near-black in light mode and `BTN_SLATE_DARK` off-white in dark, like Complete Workout; it was a faint translucent grey the sheet nearly swallowed, user decision 2026-10-02). Every Cancel in a sheet is this pill, never drawn by hand: the program and recipient pickers had their own faint copies. `selected` marks the current choice (accent ring + tick), `sub` adds a second line. The tick (and a `badge`) sit on the label's own line, right after it, never beside the whole two-line column, where the tick floated centred between the lines past the end of the longer one (user request, 2026-10-23: the Progress page's program picker; Compare's program picker had it too). An on/off SETTING is `SheetToggle` from the same file (the Workout tab's Focus Mode): control fill + grey outline when off, accent tint + accent outline when on, switch centred after the label, whole pill is the toggle. Its switch is `components/AppSwitch.tsx`, which **every** switch in the app draws (Settings, Notifications, Privacy & Security, Create Exercise): RN's native `Switch` at full size, `trackColor={{ false: isDark ? t.div : SWITCH_TRACK_LIGHT, true: ACCT }}`, white thumb, nothing else. Never a bare `Switch` with its own colours: three pages had drifted to a paler light-mode off track. The switch takes its own taps (iOS's glass knob only shows while the switch itself is touched; display-only it just slid) inside a wrapper that claims the responder, so the pill's press doesn't also fire and flip it back; a tap elsewhere on the pill toggles it too. A sheet's menu of actions is a stack of these (12pt gap), never divider rows or `NeuCard` rows. Rows that carry more than a line of text (a program's cycle chips, a people checklist with checkboxes) stay cards.
- **A search field on a page:** `components/SearchField.tsx` — the faded look: `t.field` (a faint tint of the page, `rgba(0,0,0,0.04)` light / `rgba(255,255,255,0.06)` dark) with a `t.div` hairline, a 12-radius box 44 tall, no shadow, the search glyph, the clear circle once there's text. The Journal's Programs page (`app/program-history.tsx`), Messages (`app/trainer/messages.tsx`, trainer and gym views) and a group's member search (`app/trainer/group/[id]`, both views) draw it. Since 2026-10-22 (user request) so do both My Trainers pages and Connect, each by name like Messages (`name.toLowerCase().includes`), shown once there's anyone to search, with Messages' "No people match" line when nothing does: a gym user's (`MyTrainersSection`) over the trainers AND Other Connections; a trainer's (`MyCoachesSection`) over the trainers only, the programs below untouched; Connect's under its own PEOPLE label above Requests / Pending / Connected (so it doesn't read as a second code field), narrowing all three. "Remove a trainer" hides while the search leaves no trainer showing. Both My Trainers scroll views take `keyboardShouldPersistTaps="handled"` and a `KeyboardDismissButton`. Messages and the group page had been moved to the exercise picker's white pill (`t.ctrl`, fully rounded, shadow), and went back to this (user decision, 2026-10-22); one component so they can't drift apart again. The exercise picker keeps its white pill (not part of that request).
- **A program, read-only:** `components/ProgramSnapshotView.tsx` — the cycle strip plus one card per day with its exercises, sets, rest and notes, weights expressed in the viewer's unit. Used by `app/program-view.tsx` (a program someone sent) and `app/trainer/review/[id].tsx` (a program someone asked you to review). They are the same program seen from the two ends of one flow, so they must read identically; the review screen used to list bare exercise names, leaving a trainer to judge programming they couldn't see. Both open with `components/ProgramHeaderCard.tsx` (name, weeks, training days, cycle length) under an uppercase screen title — the viewer used to show the name as its title and the rest as bare grey text on the page, so every "View" button on the trainer and group pages opened to something plainer than the review screen. Both screens also carry `components/ProgramActionFabs.tsx` (bottom-left "Open in Builder", bottom-right "Summary" — the builder's own floating pair, same geometry and colours) and `components/ProgramSummarySheet.tsx`, the read-only counterpart to the builder's Workout Summary: every cycle day with its exercise NAMES and nothing else, for "what's in this program" rather than "how is this day programmed". The builder pill is omitted where there's nothing to edit — a program sent TO you isn't yours until you accept it.
- **A group's members as faces:** `components/trainer/MemberStack.tsx` — overlapping faces, owner first (`get_group_members`' order, unanswered invites included), "+N" past four. Each group's row on both Trainer tabs draws it at 20pt, tucked close, under the group's name (the group page's banner drew it at 38pt until its redesign, 2026-10-22, which dropped the faces: its members are listed just below). Those faces load with the hub (`loadGroupFaces` in `utils/trainerHub.ts`: one `get_group_members` per group, since other people's profiles are only readable through it, kept small by the group limits; a gym user's hub makes the same read in `loadMemberGroups`, which also takes who runs each group from it) and live in its saved copy (`PTHubData.groupFaces` / `GymHubData.groupFaces`), so the rows open with them; a group without them yet says how many members instead (on a gym user's, whose group it is too). **The send sheet** (`components/trainer/RecipientPickerSheet.tsx`, Send a Program on the trainer's Programs page; user request, 2026-10-23: it drew initials where the tab shows photos) draws people the same way: each client through `Avatar` (their photo, initials without one), and under a group's name the same 20pt stack, of only the clients a tap ticks (not me, not a member who isn't my client). The stack shows only when its faces cover everyone the tap ticks, so a row never shows fewer people than it sends to; otherwise it's the count, as before.
- **Dumbbell icon:** `components/DumbbellIcon.tsx` — the single canonical 3-path SVG, its drawing kept in `constants/tabIcons.ts` (the Workout tab's icon on iOS 26 is an image rendered from it). The variant inside `app/journal.tsx`'s local `WorkoutIcon` differs subtly in its `d` path and is intentionally left local until a pixel-diff confirms equivalence.
- **Liquid Glass:** only on functional surfaces (nav/tabs/modal chrome). Always guard with `isGlassEffectAPIAvailable()` + rgba fallback. The Workout screen builds one `prevHintsById` map (per session exercise id) that feeds the card's placeholders, its checkbox copy and the Live Activity (`buildLiveActivityQueue` asks by exercise id, not name). **Last time's sets line up with a card's rows by KIND, never by position** (`prevHintsForRows`, user request 2026-10-28): the lookups return `PrevSets` (`{ warmup, working }`, each in the order lifted), and a warm-up row reads last time's warm-up of its number, a working row last time's working set of its number. By position alone, one warm-up fewer moved every working set's numbers up a row and lost the last one, usually the top set. With fewer rows of a kind than last time had sets of it, the weakest of that kind give way and the rest keep their order: the lightest, then at the same weight the fewest reps (the top-set rule, user decision 2026-10-28), so "−" (which takes the last set) leaves the better of two working sets, and a warm-up then turned into a working set shows the heavier warm-up and both working sets in their places. - `utils/cycleDrift.ts` — **how far the program's timeline has slipped from the calendar**, and the reason the rest-day marks compose. A PUSH delays everything after it (+1 day, so the program finishes a day later); a PULL spends a rest day and brings everything from it forward (−1); a plain SKIP shifts nothing and just loses that session. The two ends are asymmetric and it is the whole off-by-one: a push INSERTS a blank day so it counts **strictly before** the date being resolved (it schedules nothing itself and must not delay itself), while a pull DELETES its date so it counts **from that date inclusive** (that day takes the following day's content). `cycleDrift` is a deliberately **dumb count** over two sorted string arrays — no cycle knowledge, no date parsing. Making the reader clever (checking at resolve time that each pulled date still lands on a Rest) breaks `app/programs.tsx:handleSetWorkoutDay`, which SOLVES for `cycleOffset` by computing the natural index with it zeroed; once the drift term depends on the offset that inversion is invalid, measured at 4 of 6 target days landing on the wrong date. The "a pull must sit on a Rest" invariant is enforced on the WRITE side by `normalizeDriftDates` (`utils/workout.ts`) instead — **every path that persists a program must run it**, exactly like `canonicalizeWorkouts`, and for the same reason: a stored date silently invalidated by a neighbouring edit. It re-targets a stale pull to the next rest day rather than dropping it, so the user's "I want that day back" survives, searching a cycle further per pull, since other moves' pulls can hold the nearest rest days. The program builder's edit save skipped it, so editing which days rest let a stale pull take a workout out of the plan; it now goes through `marksAfterEdit`. A pull dated before the start is left where it is: that's history once a long hold's resume has moved the start past it, and it still pays for the move before it (dropped, the program resumed a day behind). A pull from before a hold is checked on the timeline it was made on (`cycleIndexForDate` reads that, `programAsOf`), never the shifted one, where it could look stale and be moved, re-labelling days already lived. The re-target search, and `freeRestDate`'s for a move's rest day, count days the cycle moves ON: a pushed or held day holds it still, so passing one uses none of the search (counted in calendar days, two moves and a hold used up a 3-day cycle's search and left a move with no rest day). Re-activating or duplicating a program clears all three lists: every mark predates the new `startDate` and would otherwise count as drift against day 1.

### Programs in a group — two directions, one table

Both are `shared_programs` rows carrying a `group_id`; `kind` and row count are what separate them. **`group_id` is also the whole of the "does this belong to the group" test** — a direct send to one trainer has `group_id = null` and therefore cannot appear on a group page, which is exactly the guarantee the group screens rely on.

| | `kind` | Rows | `recipient_id` | Who acts |
| --- | --- | --- | --- | --- |
| Coach → group ("Group Programs") | `share` | one per invited member | each member | sender + any coach may delete; each member accepts their own |
| Member → group ("Programs Received") | `review` | **one** | the group's owner | any coach reviews, sends back, and Removes (clears the queue) |

**Removing a group send is always the whole send** (`removeGroupSharedProgramBatch`), from the group page's card AND the program view's bin, and for the sender as well as any coach, whatever the sender's role is now. Never `removeSharedProgram` on a group row: it only knows "I sent it" vs "I received it", so an owner removing another trainer's send only hid their own copy, and a sender took out one member's copy of many. It throws when nothing it matched was deleted (a refused delete is a silent no-op to the API), and the screens show that as an alert rather than a dead button. Archiving one (`setSendBatchArchived(key, true, groupId)`) is the whole send in the same way.

A review is one row on purpose: it's a queue item, not a request for N second opinions, and N rows would mean N returned snapshots of one program with nothing to say which the member should follow. `recipient_id` is the owner only because the column is `NOT NULL` — `coaches_group()` decides who may act. That's why `loadGroupReviewPrograms(groupId)` exists: `loadSentPrograms` would only ever surface it to the owner, so any screen opening a group review passes `groupId` through to the review screen, which looks it up through the group's queue instead of an inbox.

**Three reads of the same rows, and which one a screen wants depends on how it's scoped.** `loadSentPrograms` is scoped by ADDRESS (`sender_id` / `recipient_id`), so it can't see a group review unless you're the owner — hence `!r.group_id` there, which stops the owner's hub becoming every group's backlog. `loadGroupReviewPrograms(groupId)` is one group's open queue, for that group's page. `loadMyGroupReviews()` is every open group review I'm entitled to, gathered for a coach's hub so they don't have to open each group to find work in it; it's scoped by the `shared_programs_select` POLICY rather than by the address, and drops rows I sent myself. In a group the blocker doesn't own, the blocker's phone hides the blocked member's messages (group chat, unread, previews), their programs and review requests (at the load layer in `utils/trainerStore.ts`, `loadBlockedSenderIds`, read straight from the key because moderation imports trainerStore), and marks them **BLOCKED** on the roster. **Block, unblock and `syncBlocks` run one at a time** (`oneAtATime`), each an exclusive read → server → write. So **unblocking needs the server first** and throws otherwise (lifted locally only, the next sync would put it back); Blocked Accounts dims offline and puts the row back on failure. `scripts/verify-db.ts` covers who sees and lifts a block, whose groups it empties, and which notifications it stops.
- **Trainer / Client / Both, and switching account type (migration 0041)** — a TRAINER files each trainer-account connection as their trainer, their client, or both, in `connection_roles` (the owner's alone, synced, so a new phone keeps it; `lib/connectionRoles.ts`). `utils/roster.ts:placeConnection` is the whole rule: a trainer account with no row hasn't been decided and reads as a trainer (how every one read before 0041, so an unanswered question moves nobody); a GYM account filed "trainer" is a former trainer whose note is still waiting on my choice and sits in neither list. The question (`utils/connectionRolePrompt.ts`, native alerts, one queue so it never asks twice) comes after accepting on Connect, on Connect's focus, and a moment after launch from `useTrainerHubPrefetch` (which also imports the old phone-only `TRAINER_CLIENTS_KEY` list once as "both"), so a request I SENT that was accepted later is asked about too. Removing someone filed Both removes one side only (`setConnectionRole`), never the connection; a connection that goes takes both sides' rows with it (trigger), so reconnecting asks again. **The account-type switch is `change_account_type`, never a column write**: `reconcileAccountType` rewrites `profiles.account_type` from the phone on every launch as drift repair, and a stale phone must not sever anyone's clients, so only Profile's confirmed save calls the RPC (`changeAccountType`, which falls back to the column on a server without 0041). Trainer → Gym User deletes their groups and sent programs, withdraws reviews still waiting on them, disconnects their gym-user clients (user decision), drops their own filings, and leaves everyone connected a `connection_notices` row: a trainer who had them as trainer only gets "keep as client / remove" and they're in neither list meanwhile (user decision); as Both they stay a client; as client only nothing changes. Gym User → Trainer files them as a client of every trainer who coached them (so they don't jump to My Trainers) with a note offering "also my trainer", and files those trainers as theirs. Notes show at the top of both hubs (`components/trainer/ConnectionNotices.tsx`, part of `PTHubData` / `GymHubData`), readable and dismissable by their reader only, written only by the RPC. `scripts/verify-db.ts` section 11 covers all of it, including that a bare column write does none of it.
- `constants/programs.ts`, `constants/journal.ts`, `constants/exercises.ts` — storage keys + shared types live here. Do not hardcode storage keys in screens.

### Active program → today's workout

1. Read `@avenas/programs`; find the entry with `status === "active"` (there's at most one).
2. `daysPassed = floor((midnight(today) - midnight(parseStoredDate(startDate))) / 1 day)` (rounded, see "Day arithmetic rounds"; for a past date before a hold, against the program as it stood then, `programAsOf`).
3. `dayIndex = (((daysPassed + (cycleOffset ?? 0)) mod cycleDays) + cycleDays) mod cycleDays` — handles negative results correctly.
4. `dayName = cyclePattern[dayIndex]`. If it's `"Rest"` or empty → no workout today.
5. `workoutKey = ${dayIndex}:${dayName}`. Exercises = `workouts[workoutKey] ?? []`.

The `:` in `${i}:${name}` is the separator between index and label. The matching `dayLabel` helper splits on `:` and rejoins with `slice(1).join(":")`, so a name containing `:` round-trips correctly — but prefer to avoid it.

### Day identity — a name is never an identity

The label in a workout key is decoration; the **index** makes the key unique, and `dayIds[index]` is what identifies the day to everything outside the program. Two consequences, both load-bearing:

- **A rename changes every key on that day.** Any path that rebuilds the builder's `WorkoutMap` MUST go through `canonicalizeWorkouts(map, names, isTraining)` (`utils/programDays.ts`), which carries exercises across by index. Looking the new key up directly resolves to `undefined`, and the `?? []` behind it deletes the day's exercises — that was a real data-loss bug across four separate load paths.
- **A cycle may schedule the same name twice.** Never `cyclePattern.indexOf(name)` to find a day, never dedupe a day list by name, and never match history on `workoutName` when a `dayId` is available. Use `programDays(program)` for lists and `indexOfDayId` for lookups; the Progress page matches sessions with `workoutMatchesDay` (`utils/progressStats.ts`), which prefers `dayId` and only falls back to the name for records that have none: one that names its program (a custom workout added to it) onto the first day of that name IN ITS PROGRAM (`firstInProgram`), a free workout (`""`) onto no program's day (attribution is by program, never by name), and a legacy record with no programId onto the day marked `absorbsUnidentified`, so an ambiguous record is counted once rather than on every same-named row. Under "All programs" the scope-wide `absorbsUnidentified` gave a second program's "Arms" to the first program's row and every free "Arms" to whichever program had one. The Workout tab's hints (`sessionIsOnDay`) differ on purpose for a free workout only: its numbers still feed a workout of its name. Every new program's day ids are the positional `d0…dN`, so anything matching a session to a day by `dayId` must check the program too (the Exercise History page didn't: `utils/exerciseHistory.ts` now takes `programId`).

### Editing a program that's already running

Logged history is a **snapshot and is never rewritten**. `CompletedWorkout` carries its own `exercises` and `workoutName`, and the Journal + workout-detail render those, so editing a program can't retroactively change what a past session says — same contract as swapping an exercise mid-session on the Workout screen. Only sessions logged *after* the edit use the new programming.

What the edit does change is how the Progress page groups things, decided entirely by whether the day's `dayId` survives the save (`forkChangedDayIds`, applied in `new-program.tsx:handleFinish` against `originalEdit.current`):

| Edit | `dayId` | Progress |
| --- | --- | --- |
| Day moved to another cycle slot | kept (ids permute with the day) | unchanged — the page doesn't care which cycle day a session fell on |
| Renamed only | kept | one row, relabelled; the pre-rename sessions stay on it |
| Exercises swapped only | kept | one row; the dropped exercise still lists, flagged `inProgram: false` ("Swapped out") |
| Renamed **and** exercises changed | **new id minted** | two rows: the replacement, plus the old day as a historical row |
| Day deleted from the cycle | leaves `dayIds` | its sessions become a historical row |

"Exercises changed" compares the SET of exercise names — editing sets, reps, weight or rest is programming, not a different workout, and must not fork.

Historical rows are **derived from history, not stored**: `historicalDays` reconstructs any `dayId` that has sessions but no longer exists in an in-scope program's cycle, labelling it from the most recent session's `workoutName`. They carry `isHistorical: true`, an empty `programExercises` (nothing on them can read as "swapped out" — there's no current prescription), and never absorb unidentified sessions ahead of a live day.

### Override (change-day) flow

`@avenas/today_workout_override` stores `{ date, workoutName, programId?, dayId? }`. Honor it only when `override.date` matches the effective day — stale overrides from a previous day must be ignored. Resolution goes through `resolveWorkoutForDate(program, override, dateYMD, allPrograms?)`: the day is looked up in its **source** program (`programId`, which change-day records because the user can pick a day from a non-active program), falling back to the active program when `programId` is absent (legacy override / free workout) or its program is gone. Pass the full `allPrograms` list or cross-program overrides degrade to name-only. Inside that program the slot is found by `dayId`; the `indexOf(name)` fallback (legacy / free-workout overrides) always lands on the first day of that name. A day resolved by id surfaces its CURRENT label, so a rename since the override was written shows the new name. The override key is also used by the "free workout" flow to remember the user-chosen name across reloads (no `programId` / `dayId`).

### Save flow — what triggers Home / Journal updates

When the user taps **Finish** on a workout, in order:

1. Build a `CompletedWorkout` synchronously in memory (so the locked completed view can be set on the same tick), stamping `programId` and `dayId` from the resolved workout.
2. Set `setTodaysCompletedWorkout(completed)` synchronously.
3. `await` a sequential pair of `getItem → setItem` against `@avenas/workout_history` to prepend the workout. Sequential awaits prevent rapid back-to-back finishes racing.
4. `await` the same pattern against `@avenas/workout_dates` to ensure the date is recorded once.
5. Refresh in-memory `prevByName` from the newly-written history so a same-session discard-and-restart gets correct previous-set suggestions.
6. Clear `@avenas/workout_draft` and stop the workout timer.
7. If `isFreeWorkout && addToProgram && activeProgram` is true, append the workout name to `activeProgram.extraWorkouts` in `@avenas/programs`.

Home and Journal pick up the new workout on their next `useFocusEffect`. They are read-only with respect to workout history (Journal can additionally delete journal entries, never workouts directly).

### Edit-flow change detection

`new-program.tsx` shows the "Update" button and the "Unsaved Changes" navigation prompt based on whether the working draft differs from `originalEdit.current`. **Both** surfaces must agree, so they call the same `workoutsEqual(a, b)` helper. The `WorkoutMap` comparison uses a sorted-keys JSON form because object-key insertion order is not significant.

## Conventions for new screens (e.g. the upcoming Program Page)

A new screen plugs into the contract by following these rules — break any of them and the four interlinked pages start to drift:

- Use date helpers from `utils/dates.ts`. Do not inline `MONTH_NAMES` arrays or hand-rolled `parseStoredDate`.
- Use `utils/storage.ts:getJSON/setJSON` for new persistence paths.
- Use `<DumbbellIcon />` from `components/`.
- Storage keys come from `constants/programs.ts` and `constants/journal.ts`. Do not hardcode key strings.
- Treat `parseStoredDate(...)` returning `null` as "no active program / no workout today". Never fall back to month 0.
- Identify a workout day by its `dayId`, never by its name — see "Day identity" above. Lists of days come from `programDays(program)`; lookups from `indexOfDayId`; history matching from `workoutMatchesDay`.
- For `WorkoutMap` equality checks, use the sorted-keys form (see `workoutsEqual` in `new-program.tsx`). Plain `JSON.stringify` is order-sensitive and will produce phantom diffs.
- Never block the UI on a `setItem`. Optimistic-update + rollback-on-failure is the established pattern (see `journal.tsx:saveEntries`).
- Storage errors → `if (__DEV__) console.warn("[avenas]", op, key, err)`. Do not surface as user-facing Alerts (that would change behavior).
- When mutating shared keys (`workout_history`, `workout_dates`, `programs`), serialize the read→write pair with sequential `await`s. Never `getItem(...).then(setItem(...))` without an `await` in between — that pattern races concurrent writers.
